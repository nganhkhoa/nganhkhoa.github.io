# C/C++ source code analysis

C/C++ language has no module setup, at least not until later C++ 20 (and I don't know what it is about). Without module, compilation stage is done separately and joined at linker stage. Although it works for basic compiler design, it makes source code analysis more complex. And the macro system makes analysis harder because macro can only be known at compile time.

Past works involves the following:

- compilation database
- LLVM bitcode output
- wrapping CC/CXX (or cc/c++) compiler

Each of them has their pros and cons, but at the moment, we cannot go further then this. Analysis of C/C++ language is inherently complex. And I want to give it a moment of thought on this matter.

## Past works

### Compilation database

Compilation database is generated by build tools<cite ref="https://clang.llvm.org/docs/JSONCompilationDatabase.html#supported-system"/>. The file stores all compilation command invoked, and should be a single file when using build tools. However, the database does not contains link commands invocation. In the optimal scenario, we can build the dependency graph of source files, each with their corresponding macro prcoessing. Then the analysis can run on this compilation instance.

Some tools using this database for analysis. But the link to real code is weak because static code analysis is done on this without macro processing or even headers processing. The approach is right but the information is limited.

### Wrapping compiler

Instead of invoking the compiler, some tools will wrap the compiler to capture all the compilation commands, and perform analysis or include anything else they want. Infer<cite ref=""> follows this approach to wrap their own compiler. Even though the approach sounds, it sometimes introduce dummy compilation because the wrapped compiler may introduce some unexpected pieces to the compilation pipeline.

> Legit some projects in OSS Fuzz cannot be compiled with Infer without fighting the compilation and changing the source code to be compatible.

### LLVM bitcode

Some research tools rely on LLVM bitcode analysis. Which they introduce a LLVM pass writing the bitcode before code optimizations happen and provide the pass on command invocations. At the end of the compilation, the bitcode files are used for analysis. Because all compilation information is generated to LLVM IR, the code should be final and more useful.

However, the dependency of the source files must still be built to join the bitcode together in a correct manner. Without joining the bitcode, each file can be taken out of context of their final binary (library or binary).

## Thoughts

The current analysis of C/C++ language is very limited due to the flexibility of how source code can be used, and their chain of compilation differs with each invocation, include folders, macros; and their target binary linking step, static libraries, dynamic libraries.

Is there a better way for analysis of C/C++ code bases?
